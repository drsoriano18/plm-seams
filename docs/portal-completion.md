## New migrations applied with explicit approval

Applied in this order to the shared PLM-SEAMS project on 3 November 2026:

1. `20261103132441_complete_student_portal.sql`
   - Adds optional program restrictions (`event_proposal.allowed_programs`); empty means no additional program restriction. Program-Specific mode requires a nonempty list. Exact stored student program names are used.
   - Updates `private.student_event_access`, shared by event RLS, discovery, and `register_event`. Existing university-wide and college-specific behavior is preserved unless an explicit program restriction is set.
   - Adds `get_student_event_details(eid)`, `get_student_dashboard_events()`, and `get_student_registration_history()`. Public invoker wrappers call role-checked, fixed-search-path private definer reads. Only display fields and aggregate counts are returned; proposal resources/budget/reviews and raw registration identities stay protected.
   - Details allow eligible published events, or the student's own historical registration. Historical access never grants registration eligibility.
   - Prevents duplicate venue joins from inflating counts. One confirmed booking is selected deterministically for display.
   - Extends the existing atomic `submit_proposal(proposal,schedule)` to retain program restrictions and supported optional fields. Keeps existing RLS and 15-day triggers.
   - Preserves original publication timestamps on future republishing and rejects client timestamp replacement. Existing data is not rewritten.
2. `20261103132500_student_profile_images.sql`
   - Adds `students.profile_image_path` and a private `student-profile-images` bucket.
   - Bucket accepts JPEG/PNG up to 2 MiB. Auth UUID folder policies permit only the owning linked Student to upload/read/delete. No browser UPDATE policy is needed: replacement uploads an immutable new file.
   - `set_student_profile_image(path)` validates role, folder ownership, and object existence before updating only the caller's photo reference. Does not allow students to edit college, program, identity, or role.
3. `20261103132520_organization_tasks.sql`
   - Adds `event_task` with required `due_at`, optional `starts_at`, status, and optional `parent_task_id`.
   - RLS limits organization access to its own events; Admins can manage tasks. Students and anonymous clients have no access.
   - Composite parent/event FK prevents cross-event parenting; immutable parent/identity and the FK prevent cycles. Deadlines must contain subtasks and fit inside their parents. Event locking serializes date changes. Remove subtasks before deleting a parent.
   - `save_event_task(task)` uses caller privileges/RLS; no client-supplied organization owner is trusted.

## Frontend implementation

- Student Dashboard uses the authorized dashboard RPC for real event names/types/venues. Existing own-registration and notification queries remain RLS scoped. Retry and loading states remain explicit.
- Event details uses only the dedicated detail RPC, not a partial discovery fallback or raw proposal/booking reads. Missing service and inaccessible-event messages are distinct. It shows original publication date, venue/building/floor/room/modality, actual college/program eligibility, counts, and remaining capacity.
- Registration/cancellation refresh the authoritative detail response; the UI does not guess Confirmed/Waitlisted from stale counts. A one-second clock closes start-time actions. The database remains authoritative at the exact start boundary and under concurrency.
- Profile and settings use one shared photo uploader: validate MIME/signature/size; upload new object; switch saved path; then delete the previous object. A failed reference save removes only the new object. Old-object cleanup failures are reported without undoing a successful save. Signed URLs are renewed, never stored in the database. Student header avatars, settings, and profile all load the saved photo.
- Password controls work in Student settings and the organization/Admin Account tabs. A separate nonpersistent client verifies the current password against the same Auth identity, then the active client calls Auth `updateUser`. New passwords require at least eight characters in the UI and must meet project Auth policy. Errors (including reauthentication requirements) are shown. Temporary verification sessions are signed out. No role/link/legacy password column is written; no admin key or password logging is used.
- Existing organization operations remain: `submit_proposal`, `mark_attendance`, and RLS-scoped proposal/schedule/event controls. New Tasks tab provides event tasks, subtasks, starts/deadlines/status and delete actions. Immutable parent/event fields are disabled during edits.
- Registration deadline remains the event start, as in the existing workflow. No unrelated new event status or separate registration-deadline concept was introduced.
- Figma was inspected read-only for student account settings and event details. Existing React/CSS/components/assets were retained; no Figma content or access was modified. Static screenshot text/data was not copied as real application data. These are functional integrations, not a portal redesign.
